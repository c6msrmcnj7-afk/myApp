# RecipesExplorer (iOS, SwiftUI, SPM)

A SwiftUI app that shows the DummyJSON recipes dataset. It consumes the
`recipes` Kotlin Multiplatform library **through Swift Package Manager**, not
through the Kotlin Xcode plugin: the library is linked as an XCFramework binary
target, which is exactly how an external consumer would use it.

```
iosAppSPM/
├── RecipesExplorer.xcodeproj        generated by generate-xcodeproj.py
├── Configuration/Config.xcconfig    product name, bundle id, deployment target
├── RecipesExplorer/
│   ├── App/RecipesExplorerApp.swift app entry point
│   ├── Models/RecipeItem.swift      value type mapped from the Kotlin model
│   ├── Store/RecipesStore.swift     screen state, paging, search, sorting
│   ├── Store/FavoritesStore.swift   favourites in UserDefaults
│   └── Views/                       list and detail screens
├── RecipesExplorerUITests/          XCUITest smoke tests
└── generate-xcodeproj.py            regenerates the Xcode project
```

## Prerequisites

The Swift package resolves its binary target from
`build/spm/SharedRecipes.xcframework`, which is produced by Gradle. Build it
once before opening the app:

```shell
scripts/build-xcframework.sh 0.1.0 <owner>/<repo>
```

The script also zips the framework and renders the publishable
`Package.swift`, so the same command covers local development and releases.
It needs a full Xcode installation and writes to `build/spm/`, which is
git-ignored.

## Run it

```shell
open iosAppSPM/RecipesExplorer.xcodeproj
```

Then pick the `RecipesExplorer` scheme and run. From the command line:

```shell
xcodebuild -project iosAppSPM/RecipesExplorer.xcodeproj \
  -scheme RecipesExplorer \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro' \
  -derivedDataPath build/ios-derived \
  CODE_SIGNING_ALLOWED=NO build
```

## Test it

The target `RecipesExplorerUITests` drives the real app against the live API:

```shell
xcodebuild test -project iosAppSPM/RecipesExplorer.xcodeproj \
  -scheme RecipesExplorer \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro' \
  -derivedDataPath build/ios-derived \
  -resultBundlePath build/uitest-results.xcresult \
  CODE_SIGNING_ALLOWED=NO
```

* `testListLoadsAndOpensDetail` waits for the list, opens a recipe and asserts
  that the ingredients, instructions and stat cards are on screen.
* `testSearchFiltersTheList` types into the search field and waits for filtered
  results.

Both take screenshots and attach them to the test result bundle.

## How the Swift package is wired

The app links the local package at the repository root (`.package(path: "..")`),
whose `Package.swift` points the `SharedRecipes` binary target at the built
XCFramework. The release workflow publishes a sibling manifest where that target
is a GitHub release URL plus checksum, so a consumer outside this repository
uses the very same Swift API:

```swift
.package(url: "https://github.com/<owner>/<repo>.git", branch: "spm")
```

`SharedRecipesSwift` adds the Swift friendly layer:

```swift
let repository = RecipesRepository.live()
let page = try await repository.recipes(limit: 20)
page.items.forEach { print($0.name) }        // [Recipe], already typed
let mealTypes = try await repository.mealTypes()
```

Kotlin's completion-handler API is bridged to `async`/`await` with errors
translated into `RecipesError`, so the app never touches `RecipesResult`
directly. `RecipesFailure.kind` is preserved, which the store uses to show the
failure category on the error screen.

## Regenerating the Xcode project

`project.pbxproj` is generated rather than hand-edited, so the object graph
cannot drift:

```shell
python3 iosAppSPM/generate-xcodeproj.py
```

Add a new Swift file to `SOURCE_GROUPS` in the script and re-run it. The script
also writes the shared scheme the command-line builds use.

## Screens

* **List** — paging over `GET /recipes`, sort menu (`name`, `rating`, `calories`,
  `prep time`), filter chips built from `/recipes/tags` and a scan of the
  dataset for meal types, pull to refresh, `.searchable` with a 350 ms debounce,
  and inline "could not load more" reporting.
* **Detail** — hero image, rating and review count, six stat cards (prep, cook,
  total, servings, calories, difficulty), tag chips, ingredients and numbered
  instructions, plus a favourite toggle persisted in `UserDefaults`.
